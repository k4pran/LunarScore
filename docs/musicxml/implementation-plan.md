# MusicXML 4.0 Kotlin Multiplatform parser: implementation plan

Prepared 2026-10-13. **Planning only; no parser implementation is included.** This plan is for the local LunarScore workspace and GitHub issues in `k4pran/LunarScore`. The authoritative [MusicXML 4.0 report](https://www.w3.org/2021/06/musicxml40/), [XSD](https://www.w3.org/2021/06/musicxml40/listings/musicxml.xsd/) and [4.0 version history](https://www.w3.org/2021/06/musicxml40/version-history/40/) outrank behaviour of other importers. See [architecture](architecture.md), [coverage matrix](spec-coverage.md), [test plan](test-plan.md), [reference analysis](reference-analysis.md) and [risks](risks-and-gaps.md). These documents form the design baseline; implementation issues should update them when evidence changes.

## Decisions

- Build a standalone `:musicxml-parser` with a format-neutral semantic model, rational timing, stable event IDs and structured diagnostics. Keep Compose, Android XML types and music21 out of the model.
- Use a small ordered parse representation for cursor/state and unresolved spans, then emit immutable score objects. Start with xmlutil core as the XML reader candidate; validate its security and KMP behaviour before adoption. Keep `.mxl` ZIP decoding as a separate adapter.
- Preserve written versus sounding pitch, notated versus performed duration, and musical semantics versus engraving hints. Record meaningful unsupported content explicitly.
- Run specification-based tests independently of implementation. The official XSD is a JVM/CI validation layer, not a substitute for semantic assertions.

The local `sheetmusic-core` renderer model currently supports one treble staff and simple notes. Parser output must not be constrained to that API. Use a renderer adapter later. MusicXML 4.1 work is [in progress](https://www.w3.org/community/music-notation/2026/07/27/co-chair-meeting-minutes-july-27-2026/); 4.0 remains the pinned target.

## Milestones and checkpoints

| Milestone | Issues | Demonstrable result |
|---|---|---|
| M0: evidence and contracts | MX-00–MX-04 | Pinned references, reviewed model/API, independent F01–F08 fixtures and validation harness. |
| M1: first end-to-end import | MX-05–MX-07 | A partwise XML string yields a score with one pitched note and rest at exact offsets; failure reports a location. |
| M2: core score semantics | MX-08–MX-10 | Multiple parts/staves/voices, chords, state changes and timewise equivalence. Integration checkpoint: F01–F08,F12 on supported targets. |
| M3: notation and expression | MX-11–MX-15 | Spans, tuplets, directions, lyrics and grace/cue notes with independent semantics tests. |
| M4: broad 4.0 interchange | MX-16–MX-20 | Instruments, repeats, layout, `.mxl` and 4.0 additions. |
| M5: compliance hardening | MX-21 | Coverage audit, compatibility/security corpus, documentation and target matrix. |

Complexity: S = one focused session, M = a few related components, L = split the issue into smaller PRs if it exceeds one reviewable session. An issue is complete only when its acceptance checks pass and its coverage rows and risk decisions are updated.

## Parallel work

The independent fixture author can work on MX-04 after the model projection is agreed, in parallel with MX-05/06. After MX-09, MX-11–MX-15 and MX-18 can be developed in parallel if each owns distinct event fields and shared relationship keys are frozen. MX-19 is independent of notation parsing after MX-05/06. MX-20 needs the preceding domains to distinguish implemented from unsupported additions. Merge each stream at the M1, M2, M3 and M4 checkpoints and rerun the common semantic fixtures.

**Recommended first task:** MX-00 to pin source findings and close the unresolved dependency/model questions; the first parser code task is MX-01. The first user-visible result is MX-07 at M1. Highest risks are exact timing, implicit state, cross-measure relationships, XML/ZIP security and loss during model conversion.
